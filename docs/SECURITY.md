# Security model

The browser receives a public Supabase key, never a service-role key. API handlers validate input and obtain identity from `auth.getUser()`. Sensitive operations call service-only, SECURITY INVOKER `gw_*` functions; the actor parameter comes from the authenticated server session and is never accepted from request JSON. Functions check active account status and granular permissions, then set audit identity inside the transaction. Ordinary authenticated clients cannot invoke these RPCs or directly write critical financial/state tables.

RLS protects ordinary reads/writes. Private individual/team/legal identity tables are owner/staff only; the client directory uses explicit professional-field allowlists. Pending moderation messages and their attachments remain hidden from recipients. Account suspension is enforced in RLS, including existing JWT sessions. Account type is immutable. Verification, payment, appeal and administrative fields cannot be self-edited.

Narrow private-schema lookup functions use SECURITY DEFINER only where table policies otherwise recurse or need privileged membership checks. They use fixed empty search paths and deliberate grants. The public `has_permission` helper reveals only a boolean for the authenticated user's current roles. Its deliberate SECURITY DEFINER grant generates a Supabase advisor warning; review its scope using the [advisor guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), rather than removing it blindly and breaking policies.

Files live in private buckets and are served through short-lived signed URLs after authorization. Database triggers verify owner/path relationships and object metadata before recording references. Project and dispute evidence are retained; submitted verification documents cannot be removed from their history. This is metadata and authorization validation, **not a malware scanner**. Document ingestion additionally checks PDF/DOCX signatures and caps ZIP expansion. Media transcoding, content scanning, safe previews and retention/deletion operations remain unfinished.

Financial journals balance at commit and cannot be updated/deleted through the service API. Payout and delivery state changes are serialized per project. Agreement snapshots, audit records and final dispute decisions are preserved. AI has no privileged action tools and is never an authorization boundary.

Session middleware refreshes cookies for the request and response. Sensitive API responses are private/no-store. Mutation routes reject cross-site origins. Private pages send noindex instructions; robots directives are not access controls. Dynamic user content is rendered as text, not raw HTML.

Current tests use real PostgreSQL role changes, RLS and constraints against synthetic Supabase schemas. They do not replace hosted API tests, adversarial simultaneous-request/load testing, a security assessment, or operational controls.

Before launch: enable CAPTCHA, configure [leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), require suitable staff MFA, review session retention and account deletion/export, configure email/monitoring/backups, and implement media scanning. The connected project's latest read-only advisor check reported leaked-password protection disabled. No settings were silently changed during this audit.
